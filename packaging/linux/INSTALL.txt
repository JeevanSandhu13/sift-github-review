SIFT FOR LINUX
==============

Choose a download
-----------------
Use Sift-Linux-x86_64.tar.gz for most Intel and AMD computers. Use
Sift-Linux-aarch64.tar.gz for 64-bit ARM systems. Sift supports glibc-based
desktop distributions with glibc 2.35 or newer on x86_64, or 2.39 or newer on
ARM64.

Install Sift
------------
1. Extract the complete archive.
2. Open a terminal in the extracted Sift directory.
3. On Ubuntu 24.04, install Sift's narrow AppArmor profile for bubblewrap:

     sudo ./prepare_ubuntu_host.sh

   This adds an operating-system policy for Sift. It does not disable Ubuntu's
   system-wide user-namespace protection.

4. Run:

     ./install.sh

5. Open Sift from the application menu, or run ~/.local/bin/sift.

The application installer is per-user and does not require administrator
access. It respects XDG_DATA_HOME and XDG_BIN_HOME when they are set; otherwise
it installs under ~/.local/share and ~/.local/bin. The Ubuntu preparation step
is separate and needs administrator access because it installs an AppArmor
policy.

System requirements
-------------------
Sift needs an X11 or Wayland desktop session, bubblewrap with working
unprivileged namespace confinement, and a Freedesktop Secret Service-compatible
credential vault. It also uses the normal Qt WebEngine desktop libraries for
audio, D-Bus, fonts, graphics, NSS/NSPR, udev, Wayland, X11/XKB, and XCB.

Ubuntu 24.04 uses the time64 packages libasound2t64, libevent-2.1-7t64, and
libminizip1t64. Ubuntu 22.04 uses libasound2, libevent-2.1-7, and libminizip1.
Minimal installations also need Qt WebEngine's NSS/NSPR, XCB-Dri3, and
libwayland-server0 dependencies.

Release builds are checked on Ubuntu 22.04 x86_64 and reinstalled on Ubuntu
24.04. ARM64 builds have a separate Ubuntu 24.04 qualification path. Other
distributions should pass Sift's built-in platform, renderer, and credential
checks before use with sensitive data. Sift does not disable the Qt WebEngine
sandbox to accommodate an unsupported system.

Your data and settings
----------------------
Sift does not include a model account. Connect your own provider account or
local model from Manage providers.

Credentials are stored in the desktop credential vault, not in Sift's settings
files. Imported sessions are stored in ~/.sift-sessions. A folder opened in
place keeps its private Sift state in that folder's .sift directory. Redacted
diagnostic logs use $XDG_STATE_HOME/sift/log, or ~/.local/state/sift/log when
XDG_STATE_HOME is not set. Sift contacts the update service only when you ask it
to check for an update.

Institutional policy
--------------------
Administrators can provide a root-owned policy file at:

  /etc/sift/enterprise_policy.yaml

The policy can restrict model providers, data connections, disclosure,
destinations, diagnostics, exports, and resource limits. If a configured policy
is invalid, Sift does not start the affected operation. Most users do not need
this file.

Troubleshooting
---------------
Run these checks from a desktop session:

  ~/.local/bin/sift --platform-check
  ~/.local/bin/sift --credential-store-check

The platform check covers renderer bindings, bundled assets, the 64-bit
runtime, credential integration, and bubblewrap confinement. The credential
check writes, reads, and removes a temporary test value in the desktop vault;
it never reads a provider or database credential. Your desktop may ask you to
unlock the vault.

If the platform check reports missing libraries, install the named packages
from your distribution and run it again. If it reports that bubblewrap cannot
create a namespace on Ubuntu 24.04, run prepare_ubuntu_host.sh from the extracted
release and repeat the check.

Uninstall Sift
--------------
Run:

  "${XDG_DATA_HOME:-$HOME/.local/share}/sift/uninstall.sh"

The uninstaller removes the application, launcher, desktop entry, and icons but
keeps research sessions, project .sift directories, logs, and credentials. Use
Manage providers > Forget before uninstalling if you also want to remove saved
credentials. The Ubuntu AppArmor profile remains installed because it is shared
system policy rather than user-owned application data.
